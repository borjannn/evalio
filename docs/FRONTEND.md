# Evalio — Frontend Documentation

Next.js 16.2.12 (App Router), React 19.2.4, TypeScript 6 (`strict`), Tailwind CSS
v4. Everything lives under `frontend/`.

For the wider system picture see [ARCHITECTURE.md](ARCHITECTURE.md); for the API
this consumes see [BACKEND.md](BACKEND.md). §7 below maps every screen to the
endpoints it calls.

## 1. Stack and versions

| Package | Version | Note |
| --- | --- | --- |
| `next` | 16.2.12 | App Router, `typedRoutes` enabled, Turbopack |
| `react` / `react-dom` | 19.2.4 | Server Components, Server Functions, `useActionState` |
| `typescript` | **`^6`** | Pinned — see below |
| `tailwindcss` | ^4.3.3 | **No config file.** Tokens live in CSS. |
| `lucide-react` | ^1.27.0 | The only UI dependency |

That is the entire dependency list. There is no component library, no state
manager, no data-fetching library, no animation library and no charting library.

> **TypeScript must stay on `^6`.** Next 16's built-in type checker cannot use
> TS 7 — `next build` exits and tells you to enable
> `experimental.useTypeScriptCli` — and `@typescript-eslint` peer-requires
> `<6.1.0`. A bare `npm i -D typescript` installs 7.x, so the constraint has to be
> written out.

### Scripts

```bash
npm run dev         # dev server on :3000
npm run build       # production build (also runs typegen + tsc)
npm run start       # serve the production build
npm run lint        # eslint
npm run typecheck   # next typegen && tsc --noEmit
```

`npm run typecheck` runs `next typegen` first deliberately: a bare `tsc --noEmit`
on a clean checkout fails until route types have been generated once.

## 2. This is not the Next.js you may remember

Version 16 differs from most training data and most tutorials in ways that break
code silently:

| What changed | Consequence |
| --- | --- |
| `params` and `searchParams` are **Promises** | `const { quizId } = await params;` |
| `cookies()` is **async** | `(await cookies()).get(...)` |
| Middleware is now **`proxy.ts`** at the project root | A `middleware.ts` there does nothing at all |
| `typedRoutes` is on | `<Link href>` and `router.push()` are checked against routes that actually exist |
| Page props come from **globals** | `PageProps<'/teacher/quizzes/[quizId]'>`, `LayoutProps<...>`, `RouteContext<...>` — generated by typegen, **not imported** |

`typedRoutes` has a practical implication worth stating: **you must build a route
before you can link to it.** Linking to a screen you have not created yet is a
build error, and an href assembled at runtime needs `as Route`.

`frontend/AGENTS.md` asks anyone writing frontend code to read
`node_modules/next/dist/docs/` first, for exactly these reasons.

## 4. Data flow — how a screen gets its data

Evalio uses **no client-side data fetching at all.** There is no `useEffect` +
`fetch`, no SWR, no React Query. Every screen follows one of two shapes.

### Reading: Server Component → `lib/api.ts` → Django

```tsx
// app/teacher/page.tsx  (a Server Component — no "use client")
export default async function TeacherDashboard({ searchParams }: PageProps<"/teacher">) {
  await requireTeacher();                                    // 1. authorize
  const page = pageFrom((await searchParams).page);          // 2. read the URL
  const { results: topics, count } =
    await apiGet<Paginated<Topic>>(`/topics/?page=${page}`); // 3. fetch on the server
  return <>{/* …render… */}</>;                              // 4. render to HTML
}
```

The browser receives HTML. It never sees the token, never sees the Django URL, and
makes no API call of its own.

### Writing: Server Function

```tsx
// app/teacher/actions.ts
"use server";

export async function createTopic(_state: TopicFormState, formData: FormData) {
  await requireTeacher();                                    // re-check! see below
  await apiPost<Topic>("/topics/", { name, description });
  revalidatePath("/teacher");                                // refresh the RSC cache
  return { ok: true };
}
```

The client component binds it with `useActionState`, which gives pending state and
returned errors without any fetch code.

> ⚠️ **A `"use server"` module exports public HTTP endpoints.** Being reachable
> only from a page you consider protected proves nothing about who called it. Every
> action that does more than end a session must re-check authorization itself.

> ⚠️ **A `"use server"` module may export only async functions.** An
> `export const` beside a Server Function is a build error that neither `tsc` nor
> eslint reports, because it is a bundler rule — it only surfaces when the route is
> actually requested. That is why `lib/constants.ts`, `lib/cookies.ts` and
> `lib/pagination.ts` exist as separate files.

### `lib/api.ts`

| Export | Use |
| --- | --- |
| `apiGet<T>(path)` | One request |
| `apiGetAll<T>(path)` | **Walks every page** and concatenates |
| `apiPost` / `apiPatch` / `apiDelete` | Mutations |
| `ApiError` | `.status`, `.data`, and `.formMessage` which flattens DRF's `{field: ["msg"]}` into one line |

The module is `import "server-only"`, so pulling it into a client bundle fails the
build rather than leaking the token.

### The pagination rule that is easy to get wrong

**A list being *read* needs `<Pager>`. A set being *computed against* must be
fetched whole.** The API paginates at 25 with no way to ask for everything, and
which of the two a fetch is decides the fix:

| Kind of fetch | Use | Why |
| --- | --- | --- |
| A list the user reads — topics, quizzes, classes, banks | `apiGet` + `?page=` + `<Pager>` | Without a pager it silently caps at row 25 and nothing on screen admits it |
| A set the screen computes against — checkbox targets, `<option>`s, rows a diff is taken against | `apiGetAll` | A subset produces a **wrong** answer, not a short one |

The second case is the subtle one. On the assign screen, a class on page 2 is
unassignable; worse, an *assignment* on page 2 makes an already-assigned class
render unticked, so ticking it posts a duplicate. Same reason the class roster has
no pager — the group editor draws a checkbox per enrolled student, so a student on
page 2 would read as *not in the group*.

**Client-side filtering and pagination are incompatible.** A `.filter()` over a
fetched array searches the first 25 rows and reports "no match" for row 26. When a
list gains a pager, its search moves to the server in the same change — see
`banks/bank-list.tsx`, where the term lives in `?q=` (DRF's `?search=` on the wire).

The one exception is the statistics screen, which sorts and filters client-side —
and that is safe precisely because `/api/analytics/` is deliberately unpaginated.

## 5. Design system

### Tokens live in CSS, not in a config file

Tailwind v4 has no `tailwind.config.js`. Tokens are declared in an `@theme` block
in `app/globals.css`, and that block is what generates the utilities:
`--color-muted-foreground` there is what makes `text-muted-foreground` exist.
**Change a value there, never in a component.**

Two things in that file are deliberate and easy to "fix" wrongly:

- **Font variables are `--font-inter` / `--font-space-mono`, not `--font-sans` /
  `--font-mono`.** `@theme` maps the latter onto the former. Naming the `next/font`
  variable the same as the theme variable makes the property reference itself,
  which is invalid at computed-value time.
- **There is no dark mode and no `prefers-color-scheme` block.** The token set is
  light-only; a dark block would turn the page ground black while every card stayed
  white.

### Surfaces

`--color-canvas` (#f6f8fb) is the page ground, on `<body>`. `--color-background`
(#ffffff) is the **card** surface, not the page. There is exactly one card shadow,
`--shadow-card`, and it is structural rather than decorative — a rule of "zero
drop-shadows" made screens read flat once they had three levels of nesting.
`--shadow-raised` covers the hover lift on `<Card interactive>`.

### Colour

**One brand colour, `#2563eb`, and it means "action".** `--color-primary`,
`--color-accent` and `--color-ring` are all the same blue: primary buttons, the logo
mark, links, active nav, focus rings. The greys are slate rather than neutral so
they share its cool cast. Green, amber and red survive only as **semantic status**
(Published/Draft, score bands, destructive), never as decoration.

**`--color-accent-1..6` are the one exception, and they mean "which one".** Six
hues that give a topic or class a stable identity colour. `lib/accent.ts` picks one
from the row id — deliberately from the id and not the list position, so a topic
keeps its colour when another is deleted or when you turn to page 2 — and returns
`--accent` / `--accent-soft` for a card to set on itself.

An accent may appear on a card's icon chip, its title hover, and a count that
belongs to it. It may **not** appear on a control: the button, the link and the
focus ring on an accented card all stay `--color-primary`, because that is what
still has to mean "you can act on this". The palette contains no green, amber or
red, so a topic can never accidentally look like a warning. Its ordering is
**interleaved on purpose** (blue, fuchsia, cyan, violet, pink, indigo) — rows carry
consecutive ids, so a tidy hue ramp would put three shades of magenta next to each
other on screen.

> ⚠️ **Colour may never distinguish a quiz choice in the student flow before
> submission.** The blue is for actions; correctness is never a colour until the
> feedback screen. See §6.

### Motion

**CSS keyframes in `globals.css`, not a library.** Most of it is one-shot load-in,
which `animation-delay` cascades already handle; Motion or GSAP would add ~30 kB to
reach the same place.

| Class | Effect |
| --- | --- |
| `page-enter`, `item-enter` | One-shot fade-and-rise; `item-enter` takes an inline `animation-delay` to make a cascade |
| `logo-stroke`, `logo-letter` | The mark draws itself on load |
| `logo-trace`, `logo-breathe`, `skeleton` | **Loading only** — the only looping animations |
| `logo-jolt` | Error mark, settles after one pass |
| `bar-rise`, `bar-fill`, `grid-sweep`, `mean-mark` | Chart build-in |
| `pressable` | The base hover/press response for every control |

Rules that are not negotiable:

- **Every animation is mirrored in a `@media (prefers-reduced-motion: reduce)`
  block** that collapses it to its finished state. Mandatory, not a nicety.
- **Only loading indicators loop.** A still progress indicator claims the work has
  stopped; these are also the only animations that remove themselves, because the
  element unmounts the moment data lands. Nothing that *stays* on screen may loop.
- **Bars are revealed with `clip-path`**, not `height` (which would put ten bars
  through layout every frame) and not `scaleY` (which squashes a bar's top radius
  flat while it grows and snaps it round at the end).
- ⚠️ **Tailwind v4 compiles `scale-*` and `translate-*` to the standalone `scale`
  and `translate` properties, not into `transform`.** `transition-transform` on a
  scaled element animates nothing. Name the property the utility actually sets.
- ⚠️ An element taking `pressable` must **drop its own `transition-colors`** —
  that utility sits in a later cascade layer and would narrow `transition-property`
  back to colours, killing the lift. `pressable` supplies the colour transition too.
- `pressable` is applied by hand, **never as a global `button` selector**: the
  chart's per-bar hover targets, the student runner's choices, and the drag handle
  must not lift.

### `cn()` does not merge Tailwind classes

`lib/cn.ts` is a plain string join with **no conflict resolution**. Passing `px-2`
to a component that already sets `px-4` leaves both in the class list and CSS source
order decides, unpredictably. Two consequences:

- Overrides should be layout-only (`w-full`, `mt-4`, `mx-auto`).
- To change a component's own colour or padding, add a **variant or tone to the
  component**, do not pass a conflicting class. This is why `Badge` gained a
  `tone="accent"` rather than accepting `bg-[var(--accent-soft)]`.

### The `ui/` primitives

| Component | Purpose |
| --- | --- |
| `Button` | Three variants: `primary`, `secondary`, `destructive`. Renders no state, so it works in Server *and* Client Components. |
| `Card` / `CardBody` / `CardFooter` | The surface. `interactive` adds the hover lift — only for cards that are entirely a link. |
| `Badge` | Counts and status. Tones: `neutral`, `success`, `danger`, `accent`. |
| `ScoreBadge` / `scoreFill` | The **one** banding scale (green ≥80, amber ≥50, red) shared by every screen that shows a score |
| `Field` / `Input` / `Textarea` / `Select` | Form primitives with label and hint |
| `PageHeader` / `Section` | Screens are built from these, not from hand-rolled heading rows |
| `Table` / `THead` / `TH` / `TBody` / `TR` / `TD` | Hairline-separated rows; sticky header; the wrapper scrolls horizontally |
| `Pager` | Previous/next plus "1–25 of 210". Links, not buttons, so the page survives a reload. |
| `Stat` | A headline number with a label |
| `Tally` | A number that rolls up from zero — see below |
| `EmptyState`, `Skeleton`, `PageLoader` | Empty and loading states |

**Screens are built from `<PageHeader>` and `<Section>`.** `<Section>`'s
brand-coloured tick and hairline are the "highlighted section" affordance, and they
deliberately do *not* box each section in its own card — that is what turns a page
into a stack of unrelated widgets.

**`components/ui/tally.tsx` is the one piece of motion that is JavaScript**, and the
exception is narrow: a number has to stay readable *while* it changes. The CSS route
(`@property` + `counter()`) is integer-only, renders through `::after` so the figure
is neither selectable nor reliably announced, and needs two counters glued together
to fake one decimal place. It is still one `requestAnimationFrame` loop, not a
dependency.

It seeds its state with the **target**, so the server sends the real figure and a
client without JavaScript keeps it, then rewinds to zero in a *layout* effect —
before paint — so the final number never flashes first.

> ⚠️ `Tally` renders an em dash for `null` and never animates it. Rolling a null up
> to zero would erase the "nobody submitted" / "everyone scored nought" distinction
> the whole analytics layer exists to preserve.

### Loading and error states

`loading.tsx` files create Suspense boundaries; `<Skeleton>` is used where the
layout is known ahead of time and `<PageLoader>` where it is not.

> ⚠️ **`reset()` alone does not recover a Server Component failure.** It re-renders
> the boundary's children against the same cached RSC payload and lands straight
> back on the error. `ErrorState` calls `router.refresh()` *and* `reset()` inside
> one transition. Do not "simplify" it back.

## 6. The student flow is a content boundary, not just a screen

This is the part of the frontend where a styling decision is a correctness
decision.

**In `app/student/attempts/[attemptId]/runner.tsx`, the selected choice is marked in
`foreground` — the body-text near-black — not in the brand blue and not in a
semantic tone.** Blue means "action" everywhere else in the app, so on a choice it
would read as endorsement. Blue survives only on Next and Submit. The answer-saved
indicator is the plain word "Saved". The question navigator distinguishes answered
from unanswered and nothing else. Checkmark iconography is banned outright before
submission, so selection is a dot.

**Verifying that screen means searching the RSC payload, not reading the JSX.**
Everything a Server Component passes to a Client Component is serialized and
readable in DevTools whether or not anything renders it. A student screen that
fetches the teacher shape and merely declines to display `is_correct` has still
shipped the answer key.

The compile-time half of that guard is `lib/types.guard.ts`:

```ts
type StudentChoice = { id: number; text: string; is_correct?: never; feedback_text?: never };

// Fails to compile if the `?: never` members are removed:
export type TeacherChoiceIsNotAStudentChoice =
  AssertFalse<Assignable<TeacherChoice, StudentChoice>>;
```

TypeScript is structurally typed, so without those `?: never` members a wider
teacher object would satisfy the narrower student type and the leak would be
invisible. The file has no runtime output; it exists so `npm run typecheck` fails.

**The student shell is a component the screens render, not a layout.** The runner is
an explicit exception to the nav, and a page cannot opt out of a layout. The
alternative was a `(shell)` route group putting `attempts/[attemptId]` in two places
in the tree to express one difference.

### Type ↔ serializer correspondence

`lib/types.ts` mirrors the backend serializers. The pairs that matter:

| Django serializer | TypeScript type | Carries the answer key? |
| --- | --- | --- |
| `QuizDetailTeacherSerializer` | `QuizDetailTeacher` | **Yes** — teacher routes only |
| `QuizDetailStudentSerializer` | `QuizDetailStudent` | No (`?: never` guards) |
| `QuestionTeacherSerializer` | `TeacherQuestion` | Yes |
| `QuestionStudentSerializer` | `StudentQuestion` | No |
| `QuizTeacherListSerializer` | `TeacherQuizListItem` | n/a — counts |
| `QuizStudentListSerializer` | `StudentQuizListItem` | n/a — own attempt state |
| `QuizAttemptTeacherSerializer` | `TeacherAttemptDetail` | Yes — includes snapshots |
| `QuizAttemptSerializer` | `QuizAttempt` | No |
| `FeedbackResultSerializer` | `FeedbackResult` | n/a — post-submission |
| analytics response | `Analytics = ScoreAnalytics \| AccuracyAnalytics` | n/a |

`Analytics` is a **discriminated union** narrowed on `metric`, matching the
backend's decision to name the metric rather than have the client infer it from
`group_by`.

Every paginated endpoint is typed `Paginated<T>` = `{count, next, previous, results}`.

## 8. Notable screens

### The quiz builder — `app/teacher/quizzes/[quizId]/`

The screen exists so a teacher can verify the **sequence** a student will
experience, which is why questions render flat in `order` and bank membership is
only a badge.

Drag-to-reorder lives in `question-list.tsx`, which owns the drag mechanics and
nothing else; `question-row.tsx` renders content and takes the grip's wiring as a
`handle` prop. The model is an **insertion slot** (`0..n`, "goes before item *n*"),
not a destination row — that is what the blue line draws, so the preview and the
drop cannot disagree, and both ends of the list are ordinary slots rather than
special cases.

> ⚠️ **The reorder is committed in `drop`, never in `dragend`.** `dragend` fires on
> cancel too, so committing there makes Escape reorder the quiz anyway.

**Adding questions has three paths, tabs inside one panel:** *Write a question*
(the shared `question-form.tsx`), *Add from a bank* (`bank-picker.tsx`), and
*Import JSON* (`import-panel.tsx`). Import is for turning a block of JSON — a
teacher's own or an LLM's — into questions without typing each choice; it pairs
with feedback drafting, since the import carries answers and the Suggest buttons
fill the explanations. Invalid JSON is caught client-side with a plain message
before any request; the server import is all-or-nothing and names the offending
question, so a paste never half-lands. *Write* is the default tab because a new
teacher's banks are empty, so bank-first would be a dead end on day one.

The header groups four different kinds of control: identity (title, Draft/Published
badge, rename) on the left, the two read-only side trips (Results, Assign) in a
segmented track, the state change (Publish) as a button beside it, and the one
irreversible action (Delete) alone in the card footer below the rule.

### The statistics screen — `app/teacher/analytics/`

Six groupings of the same data, all driven from the URL so a slice worth showing
someone is a link. The shape is identical every time — controls, headline tiles,
distribution, ranked rows — so changing the grouping feels like re-slicing one thing
rather than arriving somewhere new.

`analytics.metric` discriminates the union, and narrowing on it is what selects the
right tiles, the right axis label and the right row component.

Every row carries mean, **median**, range and its own small histogram on a shared
0–100 axis. That is deliberate: two classes on 65% where one is everybody-at-65 and
the other is half-at-90-half-at-40 need completely different lessons next week, and
only the spread and the shape say which is which.

The chart is remounted via a `key` when the slice changes, because a CSS animation
only runs when its element is created — React would otherwise reconcile the same ten
`<div>`s and silently swap their heights. Only the chart is keyed; keying the table
would throw away the teacher's sort and filter on every grouping change.

### The runner — `app/student/attempts/[attemptId]/runner.tsx`

See §6. Answers save as you go via a Server Function; the response deliberately does
not say whether the answer was right.

## 9. Conventions

**Where shared code goes.** A Server Function is just a module export, so anything
two routes both use moves out of the route folder rather than being duplicated:
shared `"use server"` modules to `lib/` (`lib/question-actions.ts`,
`lib/attempt-actions.ts`, `lib/student-actions.ts`, `lib/actions.ts`), shared
components to `components/` (`components/question-form.tsx`). Actions used by one
route stay in that route's `actions.ts`.

**Styling is Tailwind utilities, not CSS Modules.** Do not add `.module.css` files.
Take a class string from an existing primitive rather than composing your own — a
one-off button that differs by a padding step is how the system erodes.

**`<fieldset disabled>` disables everything inside it, including Cancel.** Gate the
destructive control, not the whole form. The question form's shared-question warning
once made backing out of an edit impossible without first accepting the warning.

**Read page numbers with `pageFrom`** (`lib/pagination.ts`). `searchParams` values
are `string | string[] | undefined`, and `Number(undefined)` is `NaN`, which Django
answers with a 404.

## 10. AI-drafted feedback

**No student screen changed.** That is the headline, and it is a consequence of
the architecture rather than an accident: drafting happens while a teacher is
authoring, so what a student receives is the same snapshotted passage
`FeedbackResult` always carried. `/student/attempts/[attemptId]/result`,
`/student/history` and the teacher's attempt review are untouched, and no pending
state, failure fallback or "generated by" label was needed on any of them.

Everything below is authoring UI.

### 10.1 Where it lives

| File | What it does |
| --- | --- |
| `app/teacher/topics/[topicId]/edit-topic.tsx` | The topic's drafting instructions — voice for every quiz in the topic |
| `components/question-form.tsx` | **Suggest** — a per-field button drafts one wrong choice; the whole-question button fills every empty one. Existing AI drafts show here, marked. |
| `app/teacher/quizzes/[quizId]/question-row.tsx` | The collapsed question view labels an AI draft *"AI draft"* rather than reading "No explanation" |
| `app/teacher/quizzes/[quizId]/feedback-panel.tsx` | Mode switch, readiness summary, bulk drafting, the gap list |
| `app/teacher/quizzes/[quizId]/actions.ts` | `setFeedbackMode`, `generateQuizFeedback`, `loadFeedbackReadiness` |
| `lib/question-actions.ts` | `suggestFeedback` — shared, so it sits in `lib/` |

### 10.2 A teacher must never wonder whether they wrote a sentence

This is the content rule of the whole feature, and three things enforce it:

- **A drafted field is marked** while it holds text the teacher did not type, and
  the mark comes off in the same keystroke they edit it — at which point it is
  theirs. This applies to text drafted in bulk too: opening a question shows its
  `ai_feedback_text` in the field, marked, and it becomes the teacher's
  `feedback_text` only when they save. Without this a bulk-drafted explanation is
  invisible in the editor while "N drafted" insists it exists.
- **The whole-question Suggest fills empty explanations only** — it discards any
  draft for a field the teacher has already written in, because losing their prose
  to a convenience button is the exact surprise this must not produce. **The
  per-field button is the deliberate exception:** pressing the button *on* a field
  is a request for a fresh draft of that one, so it replaces what is there, and the
  mark makes clear the new text is not theirs until they keep it.
- **Drafted and written are counted separately** — "5 yours · 29 drafted · 2
  missing" — and never merged into one "done" number.

### 10.3 The mode switch states its consequence

It is retroactive, so the label alone is not enough. Each direction gets its own
sentence, because they do different things to students who have already
submitted:

- → `ai`: *"Students who have already submitted keep the feedback they received."*
- → `teacher`: *"Students who have already submitted will see the written version
  instead of any drafted one."*

### 10.4 Progress is measured, not animated

Bulk drafting can take a minute, and a silent spinner reads as a hang. The panel
polls `feedback-readiness/` every two seconds while the request is in flight and
reports *"7 of 31 done"*, with a `<Spinner>` on the button and a looping sheen on
the progress track so the wait reads as active even before the first question
lands.

That number is real. Generation persists each question the moment it completes,
so a falling gap count is a measurement of work done rather than a bar timed to
look plausible. A progress indicator that is guessing gets found out at exactly
the wrong moment.

> ⚠️ **The poll is a Route Handler (`feedback-readiness/route.ts`), not the
> `loadFeedbackReadiness` Server Action** — the app's one route handler, and it
> exists for this reason. Server Actions run through a single queue, so a Server
> Action polled beside the minute-long draft action sits behind it and only reports
> once the draft is already done, making the bar jump 0 → full. A route handler is
> fetched directly and runs concurrently. It is still the BFF: it goes through
> `apiGet` and re-checks the role with `requireTeacher()`.

### 10.5 Publishing can now be refused

`setPublished` returns state instead of `void`, because a quiz in AI mode with an
unexplained wrong choice is a 400. The message lands beside the quiz title, and
the gap list naming the actual choices is already on screen in the panel below.

### 10.6 The type guard grew

`StudentChoice` gained `ai_feedback_text?: never`, and `lib/types.guard.ts` gained
three assertions — one per teacher-only member — that each field **on its own**
rejects the student shape. Without them, deleting `ai_feedback_text?: never` would
fail nothing, because `is_correct?: never` alone would keep the existing assertion
red and the leak would ship.

## 11. Adding a screen — the checklist

1. Create the route folder under `app/` with a `page.tsx`. Type its props with the
   **global** `PageProps<'/your/route'>` — do not import it.
2. `await requireTeacher()` or `await requireStudent()` as the first line.
3. `await params` / `await searchParams` — both are Promises.
4. Fetch with `apiGet` (+ `<Pager>`) or `apiGetAll`, per §4.
5. Server Component by default. Add `"use client"` only to the leaf that genuinely
   needs interactivity.
6. Build from `<PageHeader>` and `<Section>` and the `ui/` primitives.
7. Add a `loading.tsx` if the fetch is slow enough to notice.
8. If a student can reach it, use the **student** types and check the RSC payload.
9. `npm run lint` and `npm run typecheck` — and for anything touching bundler rules
   (`"use server"` exports), `npm run build`, because neither of the first two
   catches those.
